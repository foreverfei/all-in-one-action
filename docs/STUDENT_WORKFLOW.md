# 学生协作与实验反馈

本项目鼓励学生自主选择实现和分析路线。协作记录的目的，是让其他人理解证据和继续工作，
而不是检查是否按固定步骤执行。

## 1. 主 Issue

每名学生每周或每阶段维护一个主 Issue。Issue 只需写清：

- 当前问题；
- 不能改变的实验边界；
- 最低证据；
- 最终 Gate。

不需要把每天的任务、文件名或实现步骤预先写满。

## 2. 进展更新

在出现有意义的结果、方向变化或阻塞时更新 Issue，不要求每日打卡。

推荐的简短格式：

```markdown
## 进展

- 尝试了什么：
- 观察到什么：
- 证据或结果路径：
- 下一步想法 / 当前阻塞：
- commit（如有）：
```

学生可以记录失败尝试、意外现象和新假设。探索性结果需要与正式主结果区分。

## 3. 阻塞

普通阻塞直接写在主 Issue。只提供解决问题需要的信息，例如复现命令、关键错误、相关环境、
已经尝试的方向和需要的帮助。

只有影响两条任务线、`main`、CI 或正式数据时，才单独建立 Blocker Issue。

## 4. 结果总结

阶段结束时，用 Issue 评论或 `result_summary.md` 总结：

- 回答了什么问题；
- 使用了什么设置；
- 最重要的证据；
- 失败、不确定性和结论边界；
- 建议 `PASS / FAIL / REPEAT / STOP`。

格式、图表数量和案例数量由学生根据证据需要决定。

## 5. PR

PR 用于提交代码、配置、测试、文档和小型结果摘要。至少说明：

- 关联 Issue；
- 修改和动机；
- 如何验证；
- 已知限制。

教师关注证据质量和接口安全，不要求学生采用统一实现方案。

## 6. 长期分支

```text
student-a
student-b
```

每名学生维护一个长期分支。上一阶段合并后，先同步最新 `main`，再开始下一阶段工作。

## 7. 实验可追溯性

正式结果至少保留：

```text
config 或关键设置
git commit
数据 / checkpoint 版本
结果或日志路径
足以支持结论的逐样本证据
```

具体目录结构和工具由学生决定。不要提交数据集、模型权重或完整大规模 outputs。
